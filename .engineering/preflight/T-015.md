## Characterization

- T-014 established automatic read-only provider routing, selecting candidates through the explainable selector and committing atomic assignments/reservations.
- Currently, when an execution fails, the router simply marks the assignment as `RELEASED` with generic `ErrExecutionFailed` and releases reservations.
- Upstream providers encounter diverse failure modes with fundamentally different operational semantics:
  - Rate limiting (HTTP 429 / quota limits) with optional `Retry-After` headers;
  - Context window limits (prompt exceeding model context) which are non-retryable on the same model without compaction;
  - Authentication/credential failures (HTTP 401/403) which are permanent for the account;
  - Model unavailability / deprecation (HTTP 404) which is permanent for the model;
  - Transient network / 5xx server overload which is retryable with jittered exponential backoff;
  - Safety policy / content filter violations which are non-retryable application errors.
- Decision R-005 ("failover on every failure — rejected") dictates that failover must not occur blindly on every error. Instead, failure classification must determine whether to retry on the same provider, failover to an alternative candidate, trip the provider/model circuit breaker, or fail permanently.
- `harnessmodel.ProviderCircuitState` already exists in SQLite schema v15, but has not yet been hooked up to live execution failure classification and CAS updates.

## Scope

1. Create provider failure classification and retry package `internal/harness/provider/fault`:
   - `FailureKind` enumeration:
     - `FaultRateLimited`, `FaultContextLimitExceeded`, `FaultAuthentication`, `FaultModelUnavailable`, `FaultServerOverloaded`, `FaultTransientNetwork`, `FaultContentFilter`, `FaultUnknown`.
   - `Classify(err error) Classification`:
     - Parses HTTP status codes, error messages, and provider error structures.
     - Extracts advisory `RetryAfter` durations.
     - Maps to `harnessmodel.ErrorClass` and `harnessmodel.Failure`.
   - `RetryAction` enumeration:
     - `ActionRetrySameProvider`: Exponential backoff with jitter or `RetryAfter` delay.
     - `ActionFailoverAlternative`: Candidate re-selection without tripping circuit immediately.
     - `ActionTripCircuitAndFailover`: Increment consecutive failures; if threshold exceeded, transition `ProviderCircuitState` to `OPEN` and failover.
     - `ActionTerminalFail`: Permanent error, terminalize attempt.
   - `Decide(in DecisionInput) (Decision, error)`:
     - Evaluates classified failure against task envelope constraints, attempt number, breaker state, and backoff policy.
   - `CircuitManager`:
     - Monotonic CAS updates to `ProviderCircuitState` in SQLite store on success (`RecordSuccess`) and failure (`RecordFailure`).
2. Integrate provider fault handling into `internal/harness/provider/router`:
   - `Router.Execute` classifies executor errors, applies circuit breaker updates, and populates `ExecutionResult` with structured `FaultClassification` and recommended `RetryAction`.
3. Tests, benchmarks, and mutation testing:
   - Matrix tests for all error classifications (status codes, message substrings, structured provider errors).
   - Monotonic circuit breaker state transition tests in SQLite.
   - 64-way concurrent fault reporting and circuit CAS sentinel.
   - Mutation tests killing defects that bypass backoff, ignore context limit non-retryability, or corrupt circuit state.
   - CI smoke benchmark `BenchmarkFaultClassifyAndDecide1000Operations`.
